# Спецификация: Low-code QA Recorder & Playback

**Версия:** 0.4 (черновик) **Формат поставки:** расширение браузера (Chrome Extension, Manifest V3) с Side Panel **Автор:** QA-инженер (не разработчик, пишет инструмент для себя)

**Изменения в 0.4:** по итогам пройденного прототипа TipTap (этап 0.5, `prototype/checklist.md`): п. 7.2c переписан на двухканальный ввод (execCommand + chrome.debugger); добавлен принцип детерминизма (п. 1.3) и поле `expect` в формат шага; п. 6.3 дополнен многоуровневыми цепочками и новым действием `grid_select`; зафиксировано, что меню в целевом приложении не имеет клавиатурной навигации.

**Изменения в 0.3:** зафиксированы факты о целевом приложении (этап 0 выполнен, п. 1.2); условности по iframe/Shadow DOM сняты; добавлены предусловия теста (`start_url`), плейсхолдеры `{{var}}` и раздел о навигации между шагами (п. 7.6).

**Изменения в 0.2:** исправлен механизм ввода в contenteditable (execCommand вместо «настоящих клавиатурных событий»); перебор кандидатов переведён на единый таймаут шага; поле `type` разделено на `resolution` + `action`; зафиксированы позиции по Shadow DOM и iframe; нормализация текста; уточнены скриншоты; добавлен этап 0.5 (прототип TipTap).

## 1. Цель и область применения

Инструмент позволяет тестировщику один раз пройти тест-кейс руками на странице приложения, автоматически записать действия (клики, ввод текста, навигация по меню, работа с contenteditable-редакторами) в виде устойчивых к изменениям верстки шагов, и затем воспроизводить этот сценарий автоматически.

Ключевой принцип: элементы идентифицируются **по семантике кода страницы** (атрибуты, текст, структура), а не по экранным координатам.

### 1.1 Вне зоны действия v0.1

- Работа без открытого браузера (headless / CI) — выносится в отдельный движок воспроизведения на будущее, использующий тот же формат теста.
- Мультивкладочные и мультиоконные сценарии.
- Визуальное регрессионное тестирование (сравнение пикселей).
- **Shadow DOM — не поддерживается** (проверено на целевом приложении: отсутствует, п. 1.2).
- **iframe — не поддерживается** (проверено на целевом приложении: отсутствуют, п. 1.2). `all_frames` и `frame_path` не требуются.

### 1.2 Факты о целевом приложении (этап 0, зафиксировано 2026-11-24)

Целевое приложение — **«Яга»** (jaga.rt.ru, закрытый контур). Проверки выполнены вживую через браузер:

| Факт | Значение | Следствие для инструмента |
| --- | --- | --- |
| Стек | **React, SPA** (History API, переходы без перезагрузки документа) | content script переживает «мягкие» переходы; навигация между шагами — п. 7.6; для форм — спец-путь ввода в controlled inputs |
| iframe | **отсутствуют** | content script без `all_frames`; `frame_path` из формата убран |
| Shadow DOM | **отсутствует** | обычные селекторы работают; piercing-селекторы не нужны |
| Редактор | **TipTap/ProseMirror** — `div.tiptap.ProseMirror[contenteditable="true"]` | механика ввода подтверждена прототипом (этап 0.5), п. 7.2c |
| Меню | **без клавиатурной навигации** (проверено вручную: Enter/стрелки не работают даже для пользователя), многоуровневое (подменю + сетка выбора размера таблицы) | клавиатурный путь воспроизведения не нужен; обязателен trusted-ввод мыши (п. 7.2c); цепочки 3+ уровней (п. 6.3) |

### 1.3 Принцип детерминизма (нет ИИ в рантайме)

Всё, что делает плеер, сводится к трём детерминированным операциям: **найди → выполни → проверь следствие**.

- **Найди** — опрос кандидатов-селекторов по иерархии (раздел 4). Обычный `querySelector`, никакой «интерпретации» страницы.
- **Выполнил** — фиксированная процедура на тип действия (п. 7.2c).
- **Проверь следствие** — сравнение с ожидаемым результатом, записанным при записи (поле `expect`, п. 3): появился ли контейнер, изменился ли текст, появился ли блок.

Все «решения» принимаются **при записи** (кандидаты, следствия, тайминги фиксируются фактами страницы и MutationObserver), а не при прогоне. Если ни один кандидат не сработал — плеер не подбирает «похожий» элемент, а детерминированно падает: тест, прошедший «примерно», хуже упавшего. Новый тип контрола, неизвестный рекордеру, — не повод для угадывания, а повод для явного провала шага и перевыбора элемента кнопкой «Обновить селектор» (п. 8.3).

### 1.4 Вне зоны действия — ИИ

Искусственный интеллект не участвует ни в записи, ни в воспроизведении. Разведка незнакомых структур приложения (как устроено меню, какие события слушает) выполняется один раз человеком/прототипом и превращается в правила и конфиги рекордера.

**Проверка ядра логики (опционально, до сборки расширения):** черновая обкатка алгоритма резолва селекторов и MutationObserver-логики в виде юзерскрипта Tampermonkey — как лаборатория, без UI. Финальный код переносится в content script расширения.

## 3. Формат хранения теста

Тест — JSON-документ. Ниже — примерная схема одного шага.

```jsonc
{
  "test_id": "uuid",
  "test_name": "Оформление заказа",
  "created_at": "2026-09-21T10:00:00Z",
  "format_version": "0.4",

  "start_url": "https://jaga.rt.ru/space/901005",  // предусловие: перед первым шагом переходим сюда
  "vars": { "article_name": "Тестовая статья 01" }, // значения для плейсхолдеров {{var}} в шагах

  "steps": [
    {
      "step_id": "uuid",
      "order": 10,
      "group_id": "group-uuid | null",   // если шаг — часть цепочки (меню, слэш-команда)

      "resolution": "resolve | by_tag",  // стратегия поиска элемента
      "action": "click | hover | input | key | wait | assert | grid_select",
      "human_label": "Клик на 'Таблица' в слэш-меню",

      "candidates": [
        { "selector": "[data-slash-menu] >> text='Таблица'", "kind": "data-testid|id|name|tooltip|text|css|xpath" },
        { "selector": ".slash-menu-item:has-text('Таблица')", "kind": "text" },
        { "selector": "xpath:...", "kind": "xpath" }
      ],

      "within": "селектор родительского контейнера | null",

      "grid": { "row": 2, "col": 3 },    // только для action = grid_select: индексы ячейки в сетке within-контейнера

      "tag": {
        "assign_as": "qa-slash-table-option",
        "reuse_from": null
      },

      "value": "текст для ввода; поддерживает плейсхолдеры {{article_name}} — подстановка из vars при прогоне",

      "expect": {                        // ожидаемое следствие, зафиксированное при записи (п. 1.3)
        "kind": "portal_appeared | portal_closed | text_changed | url_changed | node_added | none",
        "selector": "table",             // для node_added: что должно появиться
        "text": null                     // для text_changed: ожидаемый фрагмент (normalized)
      },

      "timing": {
        "recorded_response_time_ms": 150,
        "wait_timeout_ms": 3000,
        "post_action_delay_ms": 0
      },

      "assert": {
        "expected_text_contains": "строка (если action = assert)"
      },

      "screenshot": "blob-ref | null",
      "enabled": true
    }
  ]
}
```

**Почему `resolution` и `action` разделены:** раньше единое поле `type` смешивало два измерения — способ поиска элемента (`resolve_and_act` / `act_by_tag`) и характер действия (`editor_type`, `assert`), из-за чего редактор карточки шага плодил бы спецкейсы. Теперь стратегия поиска и действие ортогональны.

**Предусловия теста:** `start_url` — обязательное поле; прогон начинается с перехода на него (иначе один и тот же тест проходит или падает в зависимости от того, где стоит браузер). Авторизация — вне зоны инструмента: используется живая сессия браузера.

**Поле `expect`:** рекордер заполняет его автоматически по фактам MutationObserver после действия (п. 6.2, п. 6.3). Это замена «понимания» результата при прогоне: плеер проверяет записанное следствие, а не интерпретирует страницу (п. 1.3).

### 3.1 Группировка (`group_id`)

Шаги с одинаковым `group_id` образуют логическую цепочку (например, раскрытие многоуровневого меню). Правила отката группы при разрыве цепочки — см. п. 6.4.

## 4. Иерархия кандидатов-селекторов

Порядок приоритета при резолве (от самого надёжного к самому хрупкому):

| # | Признак | Пример | Примечание |
| --- | --- | --- | --- |
| 1 | `data-testid` / `data-qa` | `[data-testid="checkout-btn"]` | специально для тестов, не меняется под стили |
| 2 | `id` | `#checkout` | отсеивать генерируемые (паттерн: много цифр/хэш) |
| 3 | `name` | `[name="email"]` | в основном для полей форм |
| 4 | `aria-label` / `title` / тултип-атрибуты / ARIA-роль + текст | `[aria-label="..."]`, `div[role="menuitem"]` + text | см. раздел 5; для пунктов меню — основной путь (прототип) |
| 5 | Видимый текст | `text="Оформить заказ"` | ломается при смене локализации/текста; см. нормализацию в п. 4.2 |
| 6 | Классы + тег (комбинация) | `button.btn.btn-primary` | последний осмысленный вариант; классы вида `_item_tuvtt_13` (CSS-modules) не использовать — прототип: нестабильны |
| 7 | Путь в дереве DOM (относительный CSS/XPath) | — | только как крайний fallback |

**Правило уникальности:** кандидат принимается, только если даёт ровно одно совпадение на странице (или внутри указанного `within`-контекста). Если совпадений больше одного — достраивается локальный контекст (см. п. 4.1).

### 4.1 Разрешение неоднозначности (повторяющиеся элементы)

Для списков/таблиц с одинаковыми элементами (например, кнопка "Удалить" в каждой строке):

1. Найти ближайший родительский блок с семантической границей (строка таблицы, карточка).
2. Внутри него найти уникальный текстовый якорь (название товара, артикул).
3. Итоговый селектор — составной: `within: "строка с текстом 'iPhone 15'"` + `selector: "кнопка 'Удалить'"`.

### 4.2 Нормализация видимого текста

Для кандидатов приоритета 5 (видимый текст) при записи сохраняются **оба варианта**:

- `raw` — исходный текст как есть;
- `normalized` — `trim`, схлопывание последовательных пробелов в один, замена неразрывного пробела `\u00a0` на обычный.

При резолве сначала пробуется `raw`, затем `normalized` — иначе поиск ломается на неразрывных пробелах и переносах строк, которые браузер отрисовывает иначе, чем они записаны в DOM.

## 5. Тултипы как источник селекторов

| Тип реализации | Где искать текст | Использовать для идентификации? |
| --- | --- | --- |
| Нативный `title` | Атрибут на самом элементе, всегда в DOM | Да, приоритет 4 |
| `aria-label` / `aria-describedby` | Атрибут на элементе | Да, приоритет 4 |
| JS-библиотека (Tippy/Popper/Floating UI) | Атрибут-конфиг на элементе-триггере (`data-tippy-content` и т.п.), НЕ содержимое всплывающего блока | Да — но брать с триггера, не с портала |

**Не использовать** для идентификации: текст, отрисованный только после наведения в отдельном DOM-узле (портал в конце `<body>`) — требует лишнего ожидания и не связан структурно с триггером.

Тестирование самого тултипа (проверка текста при наведении) — отдельный тип шага `assert`, не часть механизма поиска элемента.

## 6. Алгоритм записи (Recording)

### 6.1 Подготовка

Content script вешает слушатели на `document` в capture-фазе: `click`, `input`, `change`, `keydown`, `mouseenter`/`mouseleave`. Кадр для скриншота фиксируется на `mousedown` (см. п. 6.6).

### 6.2 Обработка события

1. Определить реальный интерактивный элемент (подъём от `event.target` к ближайшему `button`/`a`/`[role=button]`/`[role=menuitem]`/`[onclick]`, если клик пришёлся на вложенный `<svg>`/`<span>` — прототип: кликабельный узел пункта меню — `div[role="menuitem"]`, не текст внутри).
2. Собрать всех кандидатов по иерархии из раздела 4, включая тултип-атрибуты; текстовые кандидаты — с нормализацией (п. 4.2).
3. Проверить уникальность каждого кандидата; при необходимости достроить `within`-контекст (раздел 4.1).
4. Записать шаг с полным списком кандидатов (не только первым сработавшим).
5. По фактам MutationObserver после события заполнить `expect` (п. 3): появился портал-контейнер (`portal_appeared`), закрылся (`portal_closed`), изменился текст зоны (`text_changed`), сменился URL (`url_changed`), появился узел (`node_added` + селектор).

### 6.3 Определение цепочек (многоуровневые меню, слэш-команды)

1. Снимать снимок DOM непосредственно перед событием.
2. Через `MutationObserver` фиксировать, появился ли новый контейнер сразу после события (в целевом приложении — портал в конце `<body>`).
3. Если появился — открыть "окно ожидания" (несколько секунд бездействия). Если следующее событие происходит внутри этого нового контейнера — присвоить общий `group_id`. Если нет — закрыть группу.
4. Идентификация самого контейнера — через `aria-controls`/`aria-expanded`, связь id кнопки → id контейнера, либо "первый новый узел рядом с триггером".
5. **Многоуровневость (подтверждено прототипом):** цепочки бывают 3+ уровней — меню → подменю → сетка выбора размера. Пункт со стрелкой «›» — открывающий шаг (его следствие — `portal_appeared`), а не терминальный. Каждый уровень — отдельный шаг той же группы со своим `within`.
6. **Сетка выбора (grid picker):** ячейки не имеют текста — записывается как шаг `grid_select` с `{row, col}` (индексы ячейки внутри grid-контейнера, класс ячеек берётся из конфига приложения, напр. `_tableCell_`). Ожидаемое следствие — `node_added` (например, `table`).

### 6.4 Contenteditable-зоны (TipTap/ProseMirror)

1. Определить, что `event.target` находится внутри элемента с `contenteditable="true"` (в целевом приложении — `div.tiptap.ProseMirror`, п. 1.2).
2. Клавиатурные события **не** пишутся по одному шагу на символ — накапливаются в буфер до паузы в наборе (\~800 мс) или явного завершающего действия (клик вне зоны, Enter, потеря фокуса).
3. По завершении накопления — один шаг ввода с итоговой строкой.
4. Ввод символа `/` внутри contenteditable — триггер входа в режим "слэш-меню", далее обрабатывается как обычная цепочка (п. 6.3). Suggestion-режим виден как `<span class="suggestion">` в редакторе — рекордер использует это как признак открывшегося меню.
5. Проверка результата ввода — через сравнение `textContent` всей зоны/конкретного блока целиком (с нормализацией п. 4.2), не через отслеживание точной позиции в модели редактора.

**Прототип пройден (этап 0.5):** механика воспроизведения п. 7.2c подтверждена на живом редакторе — см. `prototype/checklist.md`.

### 6.5 Тайминги

Для каждого шага фиксируется `recorded_response_time_ms` (время между действием и появлением следующего значимого элемента). На его основе автоматически предлагается `wait_timeout_ms` (с запасом ×5–10). `post_action_delay_ms` по умолчанию 0, выставляется только вручную при редактировании.

### 6.6 Скриншоты

Кадр снимается **на `mousedown`** (до реакции приложения на клик), а не после события: `getBoundingClientRect()` элемента + `chrome.tabs.captureVisibleTab` + обрезка по координатам. Сохраняется как превью шага.

**Ограничение API:** `captureVisibleTab` имеет лимит примерно 2 вызова в секунду — при быстрой записи подряд кадры могут пропускаться; это допустимо, скриншоты — вспомогательная функция последнего этапа.

### 6.7 Ручные метки тестировщика

- «Отметить проверку» — создаёт шаг `assert` вместо шага-действия (сохраняет текущее состояние/текст элемента как эталон).
- «Пауза записи» / «Продолжить».

## 7. Алгоритм воспроизведения (Playback)

### 7.1 Инициализация

Загрузить тест. Перейти на `start_url`. Завести кэш резолва на время прогона (`Map<step_id → DOM-элемент>`), временный атрибут `data-qa-id` для быстрых обращений.

### 7.2 Цикл по шагам

Для каждого шага:

**a) Проверка кэша.** Если для шага уже есть валидный тег из более раннего резолва — сразу к пункту (c).

**b) Фаза резолва — единый таймаут на шаг.** Вместо последовательного перебора кандидатов с таймаутом на каждого (в худшем случае 7 кандидатов × 3 с = 21 с на шаг) работает **один общий `wait_timeout_ms` на шаг**: каждые 100 мс проверяются все кандидаты по порядку приоритета, берётся первый найденный.

- Найден → пометить 🟢, остановить опрос, проставить `data-qa-id`, закэшировать.
- Общий таймаут истёк, никто не найден → все кандидаты 🔴, шаг ❌, обработка провала (п. 7.4).

Так шаг с «ранним» сработавшим кандидатом резолвится за ~100–200 мс независимо от длины списка, а полноценный параллельный поиск (раздел 10) не требуется.

**c) Выполнение действия — два канала ввода (подтверждено прототипом):**

**Канал 1 — content script (без баннера), основной:**

- Ввод (обычное поле): установка `value` + `input`, либо посимвольная эмуляция. Для React controlled inputs — через нативный сеттер (`Object.getOwnPropertyDescriptor(HTMLInputElement.prototype, 'value').set`) + событие `input`, иначе React не увидит значение.
- **Ввод в contenteditable (TipTap/ProseMirror) — только через `execCommand`:**
  - текст — `document.execCommand('insertText', false, text)`;
  - Enter/абзац — `document.execCommand('insertParagraph')`.
  - **Синтетические `keydown` не работают** (проверено прототипом): редактор их игнорирует. Символ в DOM добавляет браузер как действие по умолчанию настоящего события, а ProseMirror лишь читает изменившийся DOM; `execCommand` проходит по ветке `beforeinput`, которую редактор принимает.
- `assert`: сравнение текущего состояния с эталоном (с нормализацией, п. 4.2).
- `grid_select`: поиск ячейки по индексам `{row, col}` в grid-контейнере `within`, далее — канал 2.

**Канал 2 — chrome.debugger (CDP), для мыши:**

- Клики и наведения, в том числе все пункты меню и ячейки сетки: `Input.dispatchMouseEvent` — `mouseMoved` (ховер) → `mousePressed` → `mouseReleased` по координатам центра элемента из `getBoundingClientRect()` (CSS px; DPR не трогаем — CDP работает в тех же CSS-единицах).
- **Синтетические клики (`el.click()`, dispatchEvent Mouse/Pointer) пункты меню игнорируют** (проверено прототипом) — поэтому мышь только через CDP.
- Клавиатурный ввод в меню не нужен: в целевом приложении Enter/стрелки не работают даже для живого пользователя (п. 1.2).
- **UX-компромисс:** `chrome.debugger` показывает баннер «расширение отлаживает этот браузер». Поэтому сессия отладчика поднимается **точечно на время прогона** и снимается сразу после; разрешение `debugger` запрашивается как optional и объясняется пользователю при установке.

**d) Пост-действие.** Ожидание `post_action_delay_ms`, если задано.

**e) Проверка следствия (п. 1.3).** После действия — ожидание записанного `expect` до `wait_timeout_ms`: появление/закрытие портала, изменение текста, `node_added` по селектору, смена URL. Следствие не наступило — шаг ❌ (обработка по п. 7.4), даже если само действие технически выполнилось.

**f) Проверка целостности цепочки.** Перед следующим шагом той же `group_id` — проверить, что контейнер предыдущего уровня всё ещё в DOM. Если исчез (меню закрылось само) — перезапустить группу с первого шага группы.

### 7.3 Логирование

На каждый шаг: какой кандидат сработал, время резолва, фаза (резолв / по тегу / ре-резолв), канал ввода, результат проверки следствия, скриншот «сейчас» для сравнения с «при записи».

### 7.4 Обработка провала (настраиваемо на уровне теста)

- **Stop** — остановить весь прогон (для критичных сценариев).
- **Skip** — пропустить шаг, продолжить (для необязательных проверок).
- **Soft fail** — продолжить прогон до конца, итоговый статус теста — «не пройден».

### 7.5 Финализация

Сводка: пройдено/всего, число резолвов / обращений по тегу / ре-резолвов, сохранение в историю прогонов с таймстампом.

### 7.6 Навигация между шагами

Целевое приложение — SPA (п. 1.2), переходы по нему не перезагружают документ: content script и состояние прогона переживают «мягкую» навигацию.

- **Мягкий переход (основной случай).** Шаг-клик, меняющий URL, считается завершённым после смены `location.href` + готовности следующего шага (обычный резолв с таймаутом это покрывает). Отдельного шага «ждать навигацию» не требуется.
- **Жёсткая перезагрузка (F5, открытие ссылки в новой сессии).** Content script умирает вместе со страницей. Состояние прогона (тест, текущий шаг, кэш) хранится в background (`chrome.storage.session`); content script при загрузке страницы запрашивает «есть ли активный прогон для этой вкладки» и продолжает с текущего шага.

## 8. UI-спецификация редактора тестов

### 8.1 Общая раскладка (Side Panel)

Список шагов слева (компактные строки), детали выбранного шага справа.

### 8.2 Индикация фазы шага

| Значок | Фаза | Смысл |
| --- | --- | --- |
| 🔍 РЕЗОЛВ | Первый поиск элемента | Опрос кандидатов до общего таймаута шага |
| ⚡ ПО МЕТКЕ | Повторное обращение | Мгновенно, по `data-qa-id` |
| 🔄⚠️ РЕ-РЕЗОЛВ | Метка протухла, повторный поиск | Сигнал нестабильности DOM приложения |
| 🔴 | Провал (ни один кандидат не сработал) | — |

### 8.3 Карточка шага — состав

- Действие (`action`, иконка) + человекочитаемое описание.
- Стратегия поиска (`resolution`: resolve / by tag) — отображается, не редактируется вручную.
- Статус последнего прогона.
- Миниатюра скриншота элемента.
- Список кандидатов-селекторов с индивидуальной пометкой 🟢/🔴/⚪(не пробовался).
- Ожидаемое следствие (`expect`) — отображается человекочитаемо («ждём: появление таблицы»), редактируется опционально.
- Для `grid_select` — индексы `{row, col}`, редактируемые.
- Поля таймингов (`wait_timeout_ms`, `post_action_delay_ms`) — редактируемые числовые инпуты.
- Кнопка «Обновить селектор» → открывает встроенный просмотр страницы, клик по новому элементу пересобирает список кандидатов.
- Кнопка «Запустить только этот шаг».

### 8.4 Группировка в списке

Шаги одной `group_id` сворачиваются в одну строку по умолчанию; автоматически разворачиваются, если внутри группы есть проваленный/ре-резолвленный шаг.

### 8.5 Сводка прогона (шапка над списком)

```

🔍 4 резолва   ⚡ 8 по меткам   ⚠️ 2 ре-резолва
```

## 9. Обработка edge case: меню закрывается при клике/наведении «мимо»

1. Строгая привязка поиска к `within`-контейнеру предотвращает клики в случайное место.
2. Действия внутри одной `group_id` выполняются без побочных промежуточных действий (без эмуляции физического перемещения курсора через весь экран).
3. Небольшая настраиваемая пауза между наведением на родительский и дочерний пункт (имитация естественного поведения), при необходимости. Прототип: ховер перед кликом обязателен — сетка размера открывается по наведению.
4. Проверка целостности контейнера перед каждым шагом цепочки (п. 7.2f) с полным перезапуском группы при разрыве.

## 10. Открытые вопросы / решения для будущих версий

- [ ] Формат экспорта теста для внешнего headless-движка воспроизведения (Playwright/Puppeteer-совместимый).
- [ ] История прогонов во времени — тренд по числу ре-резолвов как индикатор деградации стабильности приложения.
- [ ] Параллельный поиск нескольких кандидатов одновременно — **частично снят в 0.2** единым таймаутом шага с опросом всех кандидатов (п. 7.2b); актуально только если появятся дорогие кандидаты (например, XPath по большому DOM).
- [ ] Автоматическая точечная просьба к разработчику: список элементов без надёжного 1–2 приоритетного селектора, с готовой формулировкой запроса на добавление `data-testid`.
- [ ] Поддержка Shadow DOM (piercing-селекторы), если в целевом приложении появятся веб-компоненты (проверено 2026-11-24: отсутствуют).
- [ ] CDP `Input.insertText` (trusted-ввод текста) как замена execCommand там, где execCommand не сработает (кандидат из прототипа).
