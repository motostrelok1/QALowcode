# Этап 5d — Кэш-теги и индикация фаз

**Статус:** ждёт этап 3 **Покрывает:** п. 7.1, 7.2a, 8.2, 8.5 спецификации

## Цель

Ускорение повторных обращений к уже найденным элементам и видимая диагностика стабильности DOM: фазы 🔍/⚡/🔄⚠️, сводка прогона.

## Входит

1. **Кэш прогона (п. 7.1):** `Map<step_id → element>` на время прогона; при первом резолве элементу проставляется временный `data-qa-id`, повторное обращение идёт по тегу мгновенно (`resolution: "by_tag"`).
2. **Валидация тега:** перед действием — `element.isConnected` и видимость; протух → ре-резолв по полному списку кандидатов, фиксация фазы 🔄⚠️.
3. **Очистка:** после прогона все `data-qa-id` снимаются со страницы.
4. **Индикация (п. 8.2):** значки фаз в списке шагов и карточке; 🔴 при провале.
5. **Сводка (п. 8.5):** шапка над списком — пройдено/всего, время, счётчики резолвов / по меткам / ре-резолвов; сохраняется в `runs` (этап 4).
6. **Кнопка «Обновить селектор» (п. 8.3):** режим перевыбора — клик по элементу на странице пересобирает список кандидатов шага.

## Не входит

- Тренды ре-резолвов во времени (раздел 10) — будущая версия; данные для них уже копятся в `runs`.

## Критерии приёмки

1. Сценарий с повторным обращением к одному элементу: второе обращение — ⚡, время резолва ~0.
2. Элемент пересоздан приложением между обращениями → 🔄⚠️, шаг всё равно проходит, счётчик ре-резолвов +1.
3. После прогона на странице не осталось `data-qa-id`.
4. Сводка в шапке совпадает с построчным логом.
5. «Обновить селектор» пересобирает кандидатов, старый список заменён, шаг проходит на новом элементе.

## Риски

- `data-qa-id` может конфликтовать с атрибутами самого приложения → имя атрибута с префиксом, очистка в `finally`.
- Ре-резолв маскирует нестабильность — именно поэтому счётчик в сводке, а не тихий успех.
